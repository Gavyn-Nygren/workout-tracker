# Expo HAS CHANGED

This project is on Expo SDK 58. Read the exact versioned docs at https://docs.expo.dev/versions/v58.0.0/ before writing any code.

- Import JS tabs from `expo-router/js-tabs`. The `Tabs` export from `expo-router` is deprecated.
- If `npm run typecheck` reports route errors mentioning paths like `/../hooks/...`, the running dev server has written a stale `.expo/types/router.d.ts`. Delete that file or restart `npx expo start`; it's generated and gitignored.
- Data lives in a local SQLite database (`src/data/db/`). Screens never touch it directly: they use the hooks in `src/data/hooks.ts`, which call the `DataRepository` in `src/data/repository.ts`. Schema changes go in a new entry in the `MIGRATIONS` list in `src/data/db/schema.ts`; never edit a shipped migration.
- The spec 2.7 calculation rules live in `src/data/calculations.ts`, `records.ts`, `progress.ts` (streaks), `weekTargets.ts` (each week's streak target), `goals.ts` (goal progress, pace, reached and archived), and `badges.ts` (the badge catalog, for earning and Next up): which sets count, effective load, records, streaks, goals, and badges. Screens use these helpers instead of re-deriving, so every screen counts the same way. Every write refreshes the queries listed for it in `src/data/invalidation.ts`.
- A finished week's streak target is frozen in the `streak_weeks` table (`freezeEndedWeeks` in `sqliteRepository.ts`), so later edits can't rewrite a past streak. A new write that can change a past week's target or planned workouts must freeze first, inside its transaction, like the existing ones. `db/upgradeG310.ts` is a one-time update of data saved before G3.10.
- Progress rules (spec 2.10) live in pure modules in `src/features/progress/`: `series.ts` (points per metric, the change rule), `metrics.ts` (which metrics fit an exercise), `keyExercises.ts`, `progressFormat.ts`, `variations.ts`, and `bodyweight.ts` (trend and typo guard). Pins and saved graphs are in `Preferences.progress` (through `useProgressPrefs`), not the key-value store. A reopened workout counts as it was before the reopen (`src/data/reopen.ts`).
- Notification rules (spec 2.11) live in pure modules in `src/features/notifications/`: `notificationPlan.ts` (what should be pending), `localTime.ts` (quiet hours), `summaryTiming.ts`, `notificationCopy.ts`, `reconcile.ts` (the diff against what iOS has pending), `routing.ts` (taps), and `presentation.ts`. `runSync.ts` runs one sync, every read before any cancel; `NotificationSync.tsx` only wires the triggers. Writes reach it through the write feed (`src/data/writeFeed.ts`), which wraps the repository from `useRepository()`, so a new write method must match `WRITE_NAME` in `invalidation.ts`. The weekly summary's numbers are in `src/features/weekly/weeklySummary.ts`. Ours are matched by `data.app === 'et'` and the install id: never call cancel-all or dismiss-all, and never cancel or dismiss `'rest-alarm'`.
- Starter content lives in `src/data/content/`: the 12 programs in `templates/` (one file per program, built with `templates/helpers.ts`; `index.ts` lists them in catalog order, and `RETIRED_TEMPLATE_IDS` must never be reused), the gear map (`gear.ts`), the tour copy (`tutorial.ts`), and `validateTemplates.ts`, which `tests/templates.test.ts` runs over the catalog, so a template change must pass it. Onboarding's rules table is `src/features/onboarding/rules.ts`. After changing any of these, regenerate the review page with `node --import tsx tests/tools/writeContentReview.ts` (a test checks `CONTENT_REVIEW.md` matches). Each program's review status is in `templates/review.ts`.
- Calendar dates are local `YYYY-MM-DD` strings; timestamps are UTC. Get a date from a timestamp with `localDateOf` in `src/data/dates.ts`, never by slicing the string (that's the UTC date). The calendar engine, including push-forward shifts (`plan_shifts`), is `src/data/schedule.ts`; the week start comes from preferences (`weekStartsOn`), never a hard-coded Monday.
- Rest timer rules live in pure modules: `src/features/workout/rest.ts` (which rest follows a set, superset rounds, what's next) and `restAlarm.ts` (the rest-over notification). A blank plan rest means Auto: the exercise's remembered rest, then the Settings default. The provider changes the running rest only through `changeRest`.
- Progression rules live in a pure module, `src/features/workout/progression.ts`: what a rule suggests, misses and deloads, rounding, the reason line's wording, and undo. A planned exercise's "last time" is its own plan workout's (`slotHistory` in `history.ts`), else the exercise anywhere; the pre-fill and the PREVIOUS column both use it.
- `npm test` runs unit tests in `tests/` with Node's test runner. Tests can't import React Native or Expo modules; database tests use Node's built-in SQLite through `tests/support/nodeSqlite.ts`. `npm run typecheck` checks the app and the tests.
- The app is previewed in Expo Go and, from G4.1, in the development build ("Tracker Dev"; owner steps in `DEV_BUILD.md` at the repo root). Keep to modules "Included in Expo Go" until G4.2 adds the camera stack. Expo Go hides some native-build bugs: a sheet (`sheet()` in `src/app/_layout.tsx`) whose ScrollView is wrapped in a View draws blank in the dev build, so a scrolling sheet makes the ScrollView its top view (`tests/sheetLayout.test.ts` checks).
- Native settings live in `app.json` (the real app), `app.config.ts` (the development variant: `APP_VARIANT` unset or `development` gives "Tracker Dev" with a `.dev` bundle id) and `eas.json` (every profile sets `APP_VARIANT`). `tests/appConfig.test.ts` pins them. Any change to these files, a config plugin or a native package needs a new EAS build: tell the owner when a change does. Check the resulting Info.plist and entitlements with `npx expo config --type introspect` (read-only); never run `expo prebuild` in `client/`, since it rewrites `package.json`. Introspect starts from a stand-in Info.plist: base keys (UIRequiredDeviceCapabilities, NSAppTransportSecurity, UIApplicationSceneManifest) come from the SDK 58 template at build time, so judge only the keys app.json and the plugins add. The project is linked to EAS (`owner` and `extra.eas.projectId` in `app.json`); never run `eas init` again or change them.
